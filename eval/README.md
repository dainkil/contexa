# 평가

합성 자료(`data/synthetic/`)와 정답 라벨로 검색과 뽑기를 잰다. 여기 적는 숫자는 실제로 돌려서 나온 값뿐이다.

## 돌리기

레포 루트에서, ai 가상환경의 파이썬으로 돌린다(`contexa_ai`를 그대로 가져다 쓴다).

```
ai/.venv/bin/python -m unittest discover -s eval/tests -t .   # 채점 규칙·라벨 확인. server·모델 없이 돈다

# 아래는 server가 떠 있어야 한다(contexa.dev-seed.enabled: true)
ai/.venv/bin/python -m eval.retrieval [--k 8] [--errors]      # 검색. 모델 비용 없음
ai/.venv/bin/python -m eval.extract --oracle                  # 정답을 답으로 넣어 채점·라벨 확인. 비용 없음
ai/.venv/bin/python -m eval.extract --model 공급자:모델 [--errors]   # 실제 모델 호출. API 비용이 든다
```

결과는 `eval/results/이름-날짜시각.json`에 남는다(`--out`으로 바꿀 수 있다).
모델 API 키는 레포 루트 `.env`(`ANTHROPIC_API_KEY=...`, git이 무시한다)에서 읽는다. 셸 환경변수가 있으면 그쪽이 먼저다.

## 검색 (`retrieval.py`)

- 합성 문서를 일꾼과 같은 규칙으로 잘라 `POST /dev/eval/corpus`로 새 프로젝트에 넣는다. 작업 큐를 거치지 않으므로
  일꾼이 켜져 있어도 모델을 부르지 않는다.
- 앱과 같은 주소(`POST /api/v1/projects/{id}/context/search`)로 질문 21개를 묻는다(한국어 8, 영어 6, 아랍어 4, 섞어 씀 3).
- recall@k: 질문마다 (결과 k개 안에 든 정답 발언 수 / 정답 발언 수)를 평균한다. hit@k: 정답이 하나라도 든 질문의 비율.
- 정답 발언이 질문과 같은 언어인지 다른 언어인지 나눠 센다. 다국어 검색이 풀어야 하는 것은 뒤쪽이다.

### 기준선: 글자 검색(pg_trgm)만, k=8 (2026-11-25 측정)

| 질문 언어 | 질문 수 | recall@8 | hit@8 |
| --- | ---: | ---: | ---: |
| 한국어 | 8 | 0.667 | 0.875 |
| 영어 | 6 | 0.542 | 0.833 |
| 아랍어 | 4 | 0.375 | 0.750 |
| 섞어 씀 | 3 | 0.833 | 1.000 |
| 전체 | 21 | 0.599 | 0.857 |

- 질문과 같은 언어로 적힌 정답 발언: 28개 중 27개를 찾았다.
- 질문과 다른 언어로 적힌 정답 발언: 17개 중 하나도 찾지 못했다(0/17).
  예: "When is the event now?"는 날짜를 바꾼 한국어 발언(m4:1)을 찾지 못한다. "أحمد"는 "아흐마드 씨"(m2:6)를 찾지 못한다.
- 원본: `results/retrieval-trgm-baseline.json`

## 뽑기 (`extract.py`)

- 회의 4개를 차례로 모델에게 보여 준다. 일꾼과 같은 지시문(`prompts/extract.vN.md`), 같은 자료 모양, 같은 거르기
  (`extract.to_candidates`)를 쓴다. server에 내지 않으므로 server 검증과 "거절되면 한 번 다시 뽑기"는 들어가지 않는다.
- 회의마다 앞 회의의 정답 카드를 "이미 있는 카드"로 보여 준다. 그래서 회의 간 연결(이미 있는 안건·사람에 잇는 줄)을 따로 잴 수 있다.
- 규칙표는 server에서 받는다(`GET /internal/v1/jobs/ontology`).

재는 것

| 이름 | 뜻 |
| --- | --- |
| 카드 정밀도·재현율(종류별) | 종류가 같고 근거 발언이 겹치면 맞음. 인물·기관은 이름 표기로 맞춘다 |
| 줄 정밀도·재현율(종류별) | 양 끝과 종류가 모두 같아야 맞음 |
| 회의 간 줄 | 한쪽 끝이 앞 회의의 카드인 줄만 따로 |
| 결정 사건 종류 | 맞힌 결정 사건 중 종류(제안·확정·변경 …)까지 맞은 비율 |
| 근거 정확 | 맞힌 사건·조건·할 일 중 댄 근거가 모두 정답 근거 안에 있는 비율 |
| 확정 오분류 | 확정하지 않은 발언만 근거로 DECISION·CHANGE 사건을 낸 수 |
| 중복 | 이미 있는 카드를 새로 만든 수(이름·글자가 같을 때만 세므로 실제보다 적게 센다) |

라벨 규칙은 `data/synthetic/README.md`에 있다.

`--oracle`(정답을 답으로 넣기)은 모든 값이 1.0, 오분류·중복·버린 후보 0으로 나온다. 채점과 라벨이 맞물리는지 확인하는 용도이고 성능 수치가 아니다.

### 측정값: claude-opus-5-5, 지시문 extract.v1, 라벨 v1 (2026-11-25, 1회 실행)

| | 정밀도 | 재현율 | TP/FP/FN |
| --- | ---: | ---: | --- |
| 카드 전체 | 0.926 | 1.000 | 25/2/0 |
| 줄 전체 | 0.774 | 1.000 | 24/7/0 |
| 회의 간 줄 | 0.750 | 1.000 | 15/5/0 |

- 결정 사건 종류가 맞음 8/9, 근거 발언이 정답 안에 있음 19/19
- 확정되지 않은 발언을 확정으로 뽑음 0건, 이미 있는 카드를 새로 만듦 0건, 일꾼이 버린 후보 0건
- 토큰 수는 이 실행에서 세지 못했다(집계 버그, 고친 뒤 다시 재야 한다). 입력은 토큰 세기 API로 4회 합계 12,481로 쟀다
- 원본: `results/extract-opus-5-5-v1.json`(모델의 답 전체가 들어 있다)

틀림·놓침을 하나씩 본 결과(숫자는 위 그대로 두고 해석만 적는다)

- 놓친 필수 정답은 없다. 틀림 9건 중 모델이 분명히 틀린 것은 없고, 대부분 라벨이 좁아서 생겼다.
  - m4 `인쇄 → 아랍어 문구 검토` REQUIRES: 아랍어 발언 "인쇄 전에 아랍어 문구를 검토하겠다"(m4:3)에서 나온 맞는 줄인데 라벨에 빠졌다.
  - m4 `강당 예약 → 지훈` ASSIGNED_TO: 이름 정정 발언(m4:2)에서 이미 있는 줄을 다시 낸 것. 내용은 맞다.
  - m2 대면 제안 CONFLICTS_WITH 온라인 제안, m1 할 일 "장소 후보 더 알아보기", m3 결정 항목 "인쇄 일정"과 거기 걸린 줄 3개:
    원문으로 뒷받침되는 해석이지만 라벨에 없다.
- 종류가 틀린 1건: m3:2 "그럼 장소도 본관 강당으로 정하죠"를 라벨은 확정, 모델은 제안으로 봤다. 확정 쪽으로 넘겨짚지 않은 방향의 차이다.
- 따라서 이 자료는 모델을 가려내기에 쉽고 작다. 다음에 할 일: 라벨 다듬기(규칙을 먼저 정하고 저장된 답을 다시 채점),
  회의를 더 길고 어렵게(반례·암시적 담당·긴 문서), 여러 번 돌려 편차 재기, 더 작은 모델과 비교.
